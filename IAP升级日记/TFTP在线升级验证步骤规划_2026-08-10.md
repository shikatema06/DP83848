# TFTP 在线升级验证步骤规划

> 目标：按顺序验证 STM32F407 + DP83848 工程的 Bootloader 跳转、A/B 槽启动、TFTP 在线升级全流程。
> 前提：已按讨论结果删除 `tftp_server.c` 中多余的 `FLASH_If_Write_Boot_Request(BOOT_REQUEST_NORMAL);`。

---

## 一、验证环境准备

### 1.1 硬件

- STM32F407 开发板（带 DP83848 以太网 PHY）
- USB 转串口模块（接 USART1，用于观察启动 log）
- 网线直连 PC 或接入同一局域网交换机
- ST-Link / J-Link 烧录器

### 1.2 软件

- 当前工程已能成功编译 `DP83848_BOOT` 和 `DP83848` 两个目标
- TFTP 客户端工具（Windows 自带 `tftp.exe`，或 Linux `tftp-hpa`）
- 串口助手（波特率按工程配置，一般为 115200）
- 网络调试助手或自定义上位机（用于发送 `0x0C` 进入 Bootloader 命令）

### 1.3 网络参数确认

确认 `lwipopts.h` 和目标板实际网络参数一致，至少记录以下信息：

- 板子 IP 地址（如 `192.168.1.10`）
- PC 端 IP 地址（需与板子同网段）
- 子网掩码、网关
- TFTP 服务端口号（默认 69）
- TCP 命令端口号（工程自定义，如 7 或 23）

## 二、前置检查

在正式验证前，先确认以下两点：

1. **Bootloader 代码体积不超限**
   - 查看 `DP83848_BOOT.map`，确认 Bootloader 代码段结束地址 ≤ `0x0800BFFF`。
   - 若超过 48KB，检查是否仍使用 `-O0`，应使用 `-Os`。

2. **向量表符号正确**
   - App 的 `Core/Src/main.c` 中使用 `g_pfnVectors` 而不是 `__Vectors`。
   - 查看 App map 文件，确认 `g_pfnVectors` 地址等于对应槽起始地址。

## 三、阶段一：编译验证

### 3.1 清理并构建 Bootloader

```bash
cd c:/ST_project/DP83848
# 使用 CMake 构建 Bootloader 目标
cmake --build build --target DP83848_BOOT
```

**检查项**：

- 无编译错误、无链接错误
- 输出 `.elf` / `.bin` 文件正常生成
- 可选：用 `arm-none-eabi-size` 查看大小

### 3.2 构建 App

```bash
cmake --build build --target DP83848
```

**检查项**：

- 无编译错误、无链接错误
- App 输出正常

### 3.3 检查链接脚本

- 当前验证使用默认链接地址（一般为 `0x08000000`，老位置），不要先改 Slot A/B。
- 确认 `STM32F407XX_APP.ld` 中 FLASH 起始地址为 `0x08000000`。

---

## 四、阶段二：Bootloader 跳转验证

目标：确认 Bootloader 能正常超时跳转到位于 `0x08000000` 的 App。

### 4.1 烧录 Bootloader

- 烧录 `DP83848_BOOT.bin` 到 `0x08000000`
- 确保复位后从 `0x08000000` 开始执行

### 4.2 烧录 App 到旧位置

- 烧录 `DP83848.bin` 到 `0x08000000`
- 注意：这会覆盖 Bootloader，所以要先烧 Bootloader，再使用 ST-Link 单独烧 App 到 `0x08000000`，或者把 App 放到其他位置验证

**更安全的做法**：

- 如果 ST-Link 支持分区域烧录，先烧 Bootloader（`0x08000000` - `0x0800BFFF`），再烧 App（`0x08000000` 开始会覆盖 Bootloader，所以此方法仅用于验证 Bootloader 是否能跳转到 App，之后需要重烧 Bootloader）

或者：

- 先只烧 Bootloader，不跳验证（因为没 App）
- 然后进入阶段三，把 App 烧到 Slot A/B 验证跳转

### 4.3 观察串口输出

- 上电后应看到 Bootloader 启动 log
- 等待约 10 秒（超时时间）
- 观察是否跳转到 App，App 是否打印启动信息、是否建立网络连接

### 4.4 验收标准

- Bootloader 启动后 10 秒内未收到升级请求，自动跳转
- App 成功运行，PC 能 ping 通板子 IP
- App 能响应 TCP 命令

---

## 五、阶段三：Slot A/B 独立运行验证

目标：确认 App 链接到 Slot A 或 Slot B 后，Bootloader 能正确跳转，且 VTOR 设置无误。

### 5.1 修改 App 链接脚本到 Slot A

- 修改 `STM32F407XX_APP.ld`，将 FLASH 起始地址改为 `0x08010000`
- 重新编译 App

### 5.2 烧录

- 烧录 Bootloader 到 `0x08000000`
- 烧录 App 到 `0x08010000`

### 5.3 验证

- 上电，观察 Bootloader 是否启动 Slot A 的 App
- App 正常运行后，PC ping 板子 IP
- 通过 TCP 命令读取版本号，确认当前运行的是 Slot A 版本

### 5.4 切换到 Slot B

- 修改 `STM32F407XX_APP.ld`，将 FLASH 起始地址改为 `0x08060000`
- 重新编译 App
- 烧录 App 到 `0x08060000`
- 重复 5.3 的验证步骤

### 5.5 验收标准

- Slot A 和 Slot B 的 App 都能被 Bootloader 正确启动
- 两个槽位启动的 App 都能联网、响应命令
- 无 HardFault、无跑飞现象

## 六、阶段四：完整 IAP 流程验证

目标：通过 TFTP 把新固件写入备用槽，Bootloader 自动切换并启动新固件。

### 6.1 准备两个不同版本的 App

- **版本 A**：编译到 Slot A（`0x08010000`），版本号如 `v1.0.0`
- **版本 B**：编译到 Slot A（`0x08010000`），版本号如 `v2.0.0`（仅用于生成升级包）

注意：升级包本身仍是链接到 `0x08010000` 的二进制文件，Bootloader 会把它写到备用槽（Slot B）并自动跳转。

### 6.2 初始状态

- 烧录 Bootloader 到 `0x08000000`
- 烧录版本 A 到 Slot A（`0x08010000`）
- 上电，确认当前运行版本 A

### 6.3 触发进入 Bootloader

通过 TCP 命令发送 `0x0C`（`CMD_ENTER_BOOTLOADER`）：

- 板子收到命令后，写 `BOOT_REQUEST_UPGRADE` 到 `0x0800FFF8`
- 延时 500ms 后软复位
- 串口应观察到进入 Bootloader，开启 TFTP 服务

### 6.4 TFTP 上传版本 B

在 PC 端执行（以 Windows 为例）：

```cmd
tftp -i <板子IP> put DP83848_v2.bin
```

或 Linux：

```bash
tftp <板子IP>
mode binary
put DP83848_v2.bin
```

**观察点**：

- TFTP 传输进度正常
- 传输完成后 Bootloader 自动复位
- 复位后自动启动新版本 B

### 6.5 确认升级成功

- 通过 TCP 命令读取版本号，确认是 `v2.0.0`
- 确认当前 active slot 已切换到 Slot B

### 6.6 回滚验证

- 再次触发进入 Bootloader
- 上传一个**故意损坏**的固件（如把 bin 文件截断或改几个字节）
- 传输完成后 Bootloader 复位
- 验证：Bootloader 应检测到 CRC 失败，回滚到上一个 VALID 槽（Slot B 的 v2.0.0）

### 6.7 验收标准

- 正常固件能成功升级并切换槽位
- 损坏固件上传后，系统能回滚到旧 VALID 版本
- 整个过程中无 HardFault、无 Flash 写失败

## 七、常见问题排查

| 现象 | 可能原因 | 排查方法 |
|------|---------|---------|
| Bootloader 不跳转 | `boot_request` 仍为 UPGRADE | 读 `0x0800FFF8` 确认是否为 `0xFFFFFFFF` |
| App 启动后 HardFault | VTOR 设置错误 | 确认 `main.c` 使用 `g_pfnVectors` 而非 `__Vectors` |
| TFTP 传输失败 | 网络不通 / 防火墙 / 端口问题 | PC  ping 板子，确认 TFTP 端口 69 可达 |
| 升级后仍跑旧版本 | `iap_slot_commit` 未成功或 CRC 校验失败 | 查看串口 log，检查 CRC 计算范围 |
| Bootloader 超区 | 使用 `-O0` 编译 | 改为 `-Os` 重新编译 |
| 上传损坏固件后无法启动 | 回滚逻辑未生效 | 检查 `iap_slot_init()` 是否正常执行 rollback |

## 八、验收总结

以下全部通过，即可认为 TFTP 在线升级功能验证完成：

- [ ] Bootloader 和 App 都能独立编译通过
- [ ] Bootloader 10 秒超时后能跳转到 `0x08000000` 的 App
- [ ] App 链接到 Slot A（`0x08010000`）后能正常启动
- [ ] App 链接到 Slot B（`0x08060000`）后能正常启动
- [ ] 发送 `0x0C` 命令后设备能进入 Bootloader 并开启 TFTP
- [ ] 通过 TFTP 上传新固件后能自动切换到新槽运行
- [ ] 上传损坏固件后能回滚到旧 VALID 槽
