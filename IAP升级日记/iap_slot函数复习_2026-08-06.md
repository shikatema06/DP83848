# iap_slot 模块函数复习笔记

> 日期：2026-08-06 / 2026-08-07 更新
> 用途：睡前/次日快速恢复记忆，重点理解每个函数的功能、参数、返回值和设计意图。

---

## 一、先理解三个核心概念

### 1. 槽（Slot）

Flash 中两块用来放 App 固件的区域：Slot A 和 Slot B。

- 同一时间只有一个槽是 "active"（当前启动用的）。
- 另一个槽是 "spare"（备用，升级时用来接收新固件）。
- 升级的本质：把新固件写到 spare 槽，校验通过后让它变成新的 active。

### 2. 元数据（slot_meta_t）

每个槽对应一个元数据，记录这个槽里固件的状态：

- 是否有固件
- 固件长度
- 固件 CRC32
- 镜像状态（EMPTY / VALID / NEW / INVALID / OLD）
- 提交状态（IDLE / PENDING / DONE）

这些元数据统一存放在 sector 3（标志区），而不是槽内部。原因是：元数据会经常修改，修改 sector 3 不会破坏槽里的固件。

### 3. 启动标志（BOOT_SLOT_ADDR）

一个 32 位字，存在 sector 3 最末尾。高 16 位是 magic，低 8 位是 active 槽编号。

- 如果高 16 位不对，说明这个地址还没初始化过。
- 如果低 8 位是 0，表示 active 是 Slot A。
- 如果低 8 位是 1，表示 active 是 Slot B。
- 其他值都视为非法。

## 二、数据结构复习

### boot_slot_id_t

槽编号枚举：

- SLOT_ID_A：槽 A
- SLOT_ID_B：槽 B
- SLOT_ID_NONE：没有合法槽（比如 BOOT_SLOT_ADDR 未初始化或损坏）

### slot_img_state_t

镜像状态枚举：

- EMPTY：槽是空的，没有固件。
- VALID：固件已经通过 CRC 校验，可以启动。
- NEW：新固件已经写入，但还没提交，暂时不能启动。
- INVALID：固件 CRC 校验失败，不能用。
- OLD：曾经是 active 的旧固件，保留作为备份。

### slot_commit_state_t

提交状态枚举：

- IDLE：没有提交在进行。
- PENDING：新固件已收完，等待最终确认。
- DONE：提交完成，新槽已经变成 active。

### slot_meta_t

一个槽的元数据结构：

- magic：固定魔数，表示这个元数据是有效的，不是擦除后的默认值。
- img_len：固件实际字节数。
- img_crc32：固件 CRC32 校验值。
- img_state：镜像状态。
- commit_state：提交状态。
- reserved：保留字段，用于对齐。

## 三、每个函数的功能和含义

### 1. iap_slot_start_addr / iap_slot_end_addr / iap_slot_meta_addr

**功能：** 根据槽编号返回对应的地址。

**参数：** 槽编号（SLOT_ID_A 或 SLOT_ID_B）。

**返回值：** 对应的 Flash 地址。

**含义：**

- start_addr：这个槽里固件开始存放的位置。
- end_addr：这个槽结束的位置（不包含）。
- meta_addr：这个槽的元数据在 sector 3 里存放的位置。

**记忆点：** 这三个函数都是"查表函数"，只是把枚举映射成地址数字。

---

### 2. iap_slot_get_active

**功能：** 读取 BOOT_SLOT_ADDR，判断当前系统认为哪个槽是 active。

**参数：** 无。

**返回值：**

- SLOT_ID_A
- SLOT_ID_B
- SLOT_ID_NONE（如果 BOOT_SLOT_ADDR 非法）

**记忆点：** 它只是读一个 Flash 地址里的值，不会校验这个槽里真的有有效固件。真正判断能不能启动要调用 validate。

---

### 3. iap_slot_get_spare

**功能：** 返回当前不是 active 的那个槽。

**参数：** 无。

**返回值：**

- 如果 active 是 A，返回 B。
- 如果 active 是 B，返回 A。
- 如果 active 非法，默认返回 A（为了兼容首次启动）。

**记忆点：** 升级时往 spare 槽写新固件，就是这个函数决定的。

---

### 4. iap_slot_calc_crc

**功能：** 计算指定槽里固件的 CRC32。

**参数：** 槽编号。

**返回值：**

- 成功：CRC32 值。
- 失败（没有固件或 magic 不对）：0。

**计算范围：** 从槽起始地址开始，长度取元数据里记录的 img_len。

**新增防护：** 如果传入 SLOT_ID_NONE，直接返回 0，避免访问地址 0 导致 HardFault。

**记忆点：** 它不算元数据本身，只算固件数据。因为元数据是后来写进去的，CRC 要在写元数据之前算好。

---

### 5. iap_slot_validate

**功能：** 判断一个槽里的固件是否有效。

**参数：** 槽编号。

**返回值：**

- SLOT_IMG_EMPTY：槽是空的（magic 不对或状态为 EMPTY）。
- SLOT_IMG_VALID：CRC 校验通过，可以启动。
- SLOT_IMG_INVALID：CRC 校验失败或长度非法。

**判断逻辑：**

1. 先看 magic 对不对，不对就是 EMPTY。
2. 再看 img_state 是不是 EMPTY。
3. 再看 img_len 是否在合理范围。
4. 最后算 CRC，和元数据里存的 crc 比较。

**新增防护：** 如果传入 SLOT_ID_NONE，直接返回 INVALID，避免访问地址 0 导致 HardFault。

**记忆点：** 这是启动前必须调用的"安检函数"。

---

### 6. meta_commit（内部静态函数）

**功能：** 把两个槽的元数据以及 BOOT_SLOT_ADDR 一起写回 Flash。

**参数：**

- 槽 A 的元数据
- 槽 B 的元数据
- 新的 active 槽编号

**返回值：**

- IAP_SLOT_OK：成功。
- IAP_SLOT_ERR：失败。

**内部流程：**

1. 擦除整个 sector 3。
2. 写 Slot A 的元数据。
3. 写 Slot B 的元数据。
4. 写 BOOT_SLOT_ADDR，标记新的 active。

**记忆点：** 这是唯一真正修改 sector 3 的函数。所有会改变元数据或 active 的函数最后都调用它。

**踩坑记录：** 最初把 Slot A/B 的元数据写到了 SLOT_A_START_ADDR 和 SLOT_B_START_ADDR，也就是固件槽的起始地址，这会覆盖 App 固件前 16 字节。后来改成 SLOT_A_META_ADDR 和 SLOT_B_META_ADDR，这两个才是 sector 3 里专门放元数据的位置。

---

### 7. iap_slot_mark_new

**功能：** 当新固件接收完成后，把备用槽标记为 NEW 状态。

**参数：**

- 槽编号（一般是 spare）
- 固件长度
- 固件 CRC32

**返回值：**

- IAP_SLOT_OK：成功。
- IAP_SLOT_ERR：失败。

**含义：**

- 把这个槽的元数据改成：magic 正确、状态 NEW、提交状态 PENDING、记录长度和 CRC。
- 另一个槽的元数据保持不变。
- BOOT_SLOT_ADDR 仍然指向旧的 active，不会切换。

**记忆点：** 这是"我先记一笔账，但还不正式切换"。掉电后下次启动仍然用旧槽。

---

### 8. iap_slot_commit（已完成）

**功能：** 正式把 NEW 状态的槽切换成 active。

**参数：** 要提交的槽编号。

**返回值：**

- IAP_SLOT_OK：提交成功，active 已切换。
- IAP_SLOT_ERR：CRC 校验失败，没有切换。

**流程：**

1. 调用 validate 校验目标槽。
2. 如果校验失败：把目标槽标为 INVALID，保持旧 active。
3. 如果校验成功：把目标槽标为 VALID/DONE，把旧 active 槽标为 OLD/IDLE，BOOT_SLOT_ADDR 指向新槽。

**记忆点：** 这是"正式过户"。

---

### 9. iap_slot_rollback（已完成）

**功能：** 当当前 active 槽无效时，回滚到另一个有效槽。

**参数：** 无。

**返回值：**

- SLOT_ID_A 或 SLOT_ID_B：回滚到的槽。
- SLOT_ID_NONE：两个槽都无效。

**流程：**

1. 如果当前 active 槽是 VALID，直接返回它。
2. 否则尝试另一个槽。
3. 如果另一个槽 VALID，把 BOOT_SLOT_ADDR 指向它。
4. 如果都不行，返回 NONE。

**踩坑记录：** 最初实现只返回了 spare，但没有调用 meta_commit 把 BOOT_SLOT_ADDR 改过去，导致下次启动仍然读到旧的非法 active。后来补上 meta_commit，确保回滚结果持久化到 Flash。

**记忆点：** 这是"保险箱"。新固件启动失败后，能自动用回旧固件。

---

### 10. iap_slot_init（已完成）

**功能：** Bootloader 启动时调用一次，恢复状态一致性。

**参数：** 无。

**返回值：** 无。

**处理的情况：**

- BOOT_SLOT_ADDR 非法：找一个 VALID 槽，把它设为 active。
- active 槽不是 VALID：调用 rollback。
- 发现某个槽是 NEW/PENDING：校验它，VALID 就 commit，否则 rollback。

**踩坑记录 1：** 最初没处理 BOOT_SLOT_ADDR 非法的情况，导致 active 为 NONE 时直接调用 validate(NONE)，访问地址 0 会 HardFault。后来先判断 active == NONE，再单独处理。

**踩坑记录 2：** 判断 active 是否合法时，最初用的是 `!= INVALID`，这意味着 EMPTY 会被当成"可用"，继续往下走。后来改成 `!= VALID`，只有真正校验通过的槽才继续，否则走 rollback。

**记忆点：** 这是"开机自检"。无论上次怎么断电，它都要让系统处于一个确定可启动的状态。

## 四、容易混淆的点

### 1. BOOT_SLOT_MAGIC 和 SLOT_META_MAGIC 的区别

- BOOT_SLOT_MAGIC：存在 BOOT_SLOT_ADDR，表示"active 已经选好了"。
- SLOT_META_MAGIC：存在每个槽的元数据开头，表示"这个元数据有效"。

一个管"启动时选哪个槽"，一个管"这个槽里有没有有效信息"。

### 2. 为什么 meta 不放在槽里

因为修改元数据需要先擦除 sector。如果元数据放在槽里，改一次就要擦整个槽，固件就没了。所以元数据放在 sector 3，和固件槽分开。

### 3. mark_new 为什么不切换 active

因为 mark_new 时新固件还没经过最终校验。如果 mark_new 就切 active，万一 CRC 算错了，下次启动就会用坏固件。所以切换 active 放在 commit 里。

### 4. 双阶段提交的好处

- mark_new：状态变成 NEW/PENDING。
- commit：状态变成 VALID/DONE，同时切换 active。

任何一步掉电，下次 init 都能判断出现在处于哪个阶段，然后继续或回滚。

### 5. BOOT_SLOT_ENCODE 的作用

`BOOT_SLOT_ENCODE(active)` 展开是 `BOOT_SLOT_MAGIC | ((active) & 0xFFU)`。

它的作用是**截断 active 到最低 8 位**，保护高 16 位 magic 不被污染。如果直接 `BOOT_SLOT_MAGIC | active`，而 active 又是带符号的 int 且有高位扩展，可能会破坏 magic。

### 6. 从 Flash 读取结构体到 RAM 的写法

`meta_a = *(slot_meta_t *)iap_slot_meta_addr(SLOT_ID_A);`

拆解：

1. `iap_slot_meta_addr(A)` 返回一个地址数字。
2. `(slot_meta_t *)` 把数字解释成结构体指针。
3. `*` 取出指针指向的内存内容（16 字节）。
4. 赋值给 RAM 里的本地变量 `meta_a`。

修改 `meta_a` 改的是 RAM 副本，不会动 Flash。只有调用 `meta_commit()` 才会把修改后的内容写回 Flash。

### 7. 什么时候需要擦 Flash

只要看到 `xxx->field = value`，先判断 `xxx` 指向 RAM 还是 Flash：

- 指向 RAM（本地变量）：直接赋值，不需要擦 Flash。
- 指向 Flash 地址（如 0x0800xxxx）：不能直接赋值，必须用 `FLASH_If_Write`，而写之前通常要擦 sector。

## 六、整体设计流程与设计思路

### 1. 为什么需要 A/B 双备份

传统单槽升级的风险在于：新固件写入过程中一旦掉电，旧固件可能已经被破坏，设备就变砖。

A/B 双备份的核心思想是：

- 任何时候都保留一份"已知可用"的旧固件。
- 新固件先写到另一个槽，校验通过后再切换。
- 即使新固件写入失败或校验失败，Bootloader 仍然可以回滚到旧槽启动。

这样升级过程可以被打断任意次，系统始终能恢复到一个可启动状态。

### 2. 为什么把元数据放在 sector 3

Flash 的写入规则是：只能把 1 改成 0，不能直接把 0 改成 1。要修改已有数据，必须先擦除整个 sector。

如果元数据放在 App 槽里，那么：

- 每次升级更新元数据都要擦除整个 App 槽。
- 即使只是想改一个状态字节，也会导致槽内固件全部丢失。
- 升级过程中元数据更新和新固件写入耦合在一起，风险很高。

所以把元数据统一放在 sector 3（标志区），和固件槽物理隔离：

- 改状态只擦 sector 3，不动固件。
- 掉电时最多 sector 3 状态不一致，固件本身完整。
- 上电后 init 可以根据元数据恢复一致性。

### 3. 双阶段提交的设计原因

升级不是"写完固件就立刻切换"，而是分成两个阶段：

**第一阶段 mark_new：** 新固件接收完成后，把 spare 槽标记为 NEW/PENDING，但不切换 active。

**第二阶段 commit：** 再次校验新固件 CRC，通过后才把 active 切到新槽。

这样设计的原因是：

- 接收完成和最终启动之间可能还有校验、比对等操作。
- 如果 mark_new 就切换 active，万一后续发现 CRC 错误，系统已经用坏固件启动了。
- 双阶段让"写固件"和"切换启动槽"成为两个原子决策点，每个点都可以独立回滚。

### 4. BOOT_SLOT_ADDR 的作用

BOOT_SLOT_ADDR 是启动决策的"最终仲裁者"。

- 它只存一个 32 位字：高 16 位是 magic，低 8 位是 active 槽编号。
- Bootloader 启动时只需要读这一个地址，就能知道从哪个槽启动。
- 所有状态切换最终都要落到这里，否则下次启动不会生效。

为什么不用更复杂的结构？

- 越小越可靠。一个 32 位字的写入原子性最好。
- 配合 sector 3 里的元数据，足够表达全部启动信息。

### 5. 掉电恢复设计

iap_slot 的设计假设是：任何时刻都可能掉电，下次上电必须能恢复。

可能的断电状态：

| 断电时刻 | 状态 | 下次 init 行为 |
|----------|------|----------------|
| 正在接收新固件 | 固件不完整，元数据未更新 | 用旧 active 启动 |
| mark_new 刚完成 | spare 为 NEW/PENDING，active 仍指向旧槽 | 用旧槽启动，spare 保留待提交 |
| commit 过程中 sector 3 被擦除 | BOOT_SLOT_ADDR 暂时失效 | 扫描 VALID 槽恢复 active |
| commit 成功 | 新槽为 VALID/DONE，旧槽为 OLD | 从新槽启动 |
| commit 失败 | 新槽为 INVALID，旧槽仍为 VALID | 回滚到旧槽 |

`iap_slot_init()` 就是处理所有这些可能性的入口。

### 6. 为什么用软件 CRC32

- stm32f4xx_hal_conf.h 中没有启用 HAL_CRC_MODULE_ENABLED。
- 为了不改 CubeMX 生成的配置，避免后续重新生成代码时冲突。
- 软件 CRC32 计算量不大，只在启动和升级完成时执行，不影响运行性能。
- 多项式选用 Ethernet CRC32（0xEDB88320），与 tftp_server.c、net_config.c 保持一致，便于上位机工具复用。

### 7. 为什么把 iap_slot 放在 Bootloader 目录

- 槽的选择、提交、回滚是 Flash 级别的启动决策，不应该暴露给 App。
- App 只负责"请求进入 Bootloader"和"通过 TFTP 传固件"，不应该知道 A/B 槽的存在。
- 把 iap_slot 限制在 Bootloader 内，App 的代码更干净，也避免 App 误操作启动标志。

### 8. 状态转换总览

```
EMPTY  ──写入固件──>  NEW/PENDING  ──commit 成功──>  VALID/DONE  ──被新槽替换──>  OLD/IDLE
                         │                              │
                         │ commit 失败                   │ 校验失败
                         ▼                              ▼
                    INVALID/IDLE                    INVALID/IDLE
```

- EMPTY：槽还没用过。
- NEW/PENDING：新固件已写入，等待提交。
- VALID/DONE：校验通过，可以作为 active 启动。
- OLD/IDLE：曾经是 active，现在作为备份。
- INVALID/IDLE：校验失败，不可启动。

### 9. 升级全流程

1. App 收到升级命令，写 boot_request 请求重启。
2. Bootloader 启动，调用 `iap_slot_init()` 恢复状态。
3. Bootloader 发现需要进入升级模式，启动 TFTP server。
4. TFTP 收到 WRQ，调用 `iap_slot_get_spare()` 获取备用槽起始地址。
5. TFTP 把数据依次写入备用槽。
6. 传输完成，计算 CRC，调用 `iap_slot_mark_new(spare, len, crc)`。
7. 上位机或系统触发提交，调用 `iap_slot_commit(spare)`。
8. commit 校验通过，active 切换到新槽，Bootloader 重启。
9. 启动后 `iap_slot_init()` 确认新槽 VALID，从新槽启动。

如果任何一步失败：

- 写入失败：备用槽数据不完整，下次仍从旧槽启动。
- mark_new 后掉电：下次从旧槽启动，spare 保留 NEW/PENDING，可重新 commit。
- commit 校验失败：新槽标为 INVALID，回滚到旧槽。
- 新槽启动后崩溃：看门狗复位后 `iap_slot_init()` 发现 active 无效，自动 rollback。
