## 二、烧写产物是怎么生成的

编译只产出 ELF，**烧写文件是本机脚本后处理出来的**：

```
cmake --build build/Debug
 ├── DP83848.elf                      App，链接在 0x08010000（Slot A）
 └── Bootloader/DP83848_BOOT.elf      Bootloader，链接在 0x08000000
```

后处理链（`DP83848/.vscode/flash_both.cmd`）：

| 步骤 | 命令 | 作用 |
|---|---|---|
| 1 | `arm-none-eabi-objcopy -O binary DP83848.elf DP83848.bin` | ELF → 纯二进制，**丢掉地址信息**，烧写时须显式给 `0x08010000` |
| 2 | `arm-none-eabi-objcopy -O ihex DP83848_BOOT.elf DP83848_BOOT.hex` | Bootloader → Intel HEX（自带地址，便于插记录） |
| 3 | `python patch_hex.py DP83848_BOOT.hex` | 预置 Slot 元数据（见下） |
| 4 | `ST-LINK_CLI -c SWD -ME` | 全片擦除 |
| 5 | `ST-LINK_CLI -c SWD -P DP83848_BOOT.hex -V` | 烧 Bootloader（hex 自带地址，含 meta） |
| 6 | `ST-LINK_CLI -c SWD -P DP83848.bin 0x08010000 -V` | 烧 App（bin 必须显式给地址） |
| 7 | `ST-LINK_CLI -c SWD -Rst` | 复位运行 |

### 2.1 `patch_hex.py` 到底做了什么

**Bootloader 自己不会写 Slot 元数据**，所以必须在烧写前把它预置进 Flash。脚本先对 App 的 bin 算：

- `img_len` = bin 字节数
- `img_crc32` = zlib 标准 CRC32（多项式 `0xEDB88320`，与 `Bootloader/iap_slot.c` 里手写的实现一致）

然后把 48 字节拼成一条 Intel HEX 记录，插在文件尾部 EOF 记录之前，落在 **`0x0800FFD0`**：

| 地址 | 内容 | 本次实测值 |
|---|---|---|
| `0x0800FFD0` | Slot A meta: magic(4) + img_len(4) + img_crc32(4) + img_state(1) + commit_state(1) + reserved(2) | `49415053` `00017134` `ED77943D` `01` `00` `0000` |
| `0x0800FFE0` | Slot B meta（为空） | 全 `0` |
| `0x0800FFF0` | reserved，保持擦除态 | `FF` × 12 |
| `0x0800FFFC` | boot_slot word（active = A） | `55AA0000` |

其中 `0x00017134` = 94516 = `DP83848.bin` 长度，**两者必须一致**，否则 CRC 校验必败。

### 2.2 为什么 App 用 bin、Bootloader 用 hex

脚本注释里给了原因，值得记住：

- **App 用 bin**：bin 会把段间空洞保留成 `0x00`；且避免 HEX 记录跨 `0x0800FFFF → 0x08010000` 这个 64 KB 边界被拆记录的麻烦。
- **Bootloader 用 hex**：hex 是文本、自带地址，脚本可以方便地往里插额外记录。
- 两者都可用，但**App 必须用 bin + 显式地址**（`-P xxx.bin 0x08010000`）。

### 2.3 三个 VSCode 任务的分工

| 任务 | 实际内容 |
|---|---|
| `Build` | 只跑 `cmake --build DP83848/build/Debug` |
| `Flash Both (Bootloader + App + boot_valid)` | 上面 **1→7 全流程**；**首次烧写、换硬件版本、App 内容变化后要脱机运行时使用** |
| `Flash App Only (no erase)` | 只做 1 + 6（objcopy 后烧 `0x08010000`）；**不擦除、不 patch meta**（→ 见第五节隐患） |

## 三、执行过程与排障时间线

### 3.1 现象

`Build` + `Flash Both` 执行完毕，任务无报错，但 `ping 172.16.1.69` 不通。

### 3.2 第一步：读回 Flash 自证烧写无误

```powershell
$cli = "C:\Program Files (x86)\STMicroelectronics\STM32 ST-LINK Utility\ST-LINK Utility\ST-LINK_CLI.exe"
& $cli -List
& $cli -c SWD -r32 0x0800FFD0 12
& $cli -c SWD -r32 0x0800FFF0 4
& $cli -c SWD -r32 0x08000000 2
& $cli -c SWD -r32 0x08010000 2
& $cli -c SWD -Rst
```

实测输出：

| 地址 | 读到 | 判读 |
|---|---|---|
| `0x0800FFD0` | `49415053 00017134 ED77943D 00000001` | meta 正确：magic ✓、`img_len` 与 bin 一致 ✓、CRC ✓、state=VALID ✓ |
| `0x0800FFE0` | `00000000` | Slot B 为空 ✓ |
| `0x0800FFF0` | `FFFFFFFF` | reserved 为擦除态 ✓（`0x0800FFF8` 的 boot_request 因此不是 `0x55AA55AA`，不会误入 IAP 模式） |
| `0x08000000` | `20020000` | Bootloader 向量表在，SP 合法（128 KB RAM 顶）✓ |
| `0x08010000` | `20020000` | **App 向量表确实在 Slot A，SP 合法 → App 已烧入** ✓ |

**结论：烧写侧无问题**，问题排除到运行/网络侧。

> 注：`ST-LINK_CLI v3.6` 的 `-r32 <addr> <n>` 实测**每次只回 1 个 word**，要逐个地址读。

### 3.3 第二步：查 PC 侧

```powershell
Get-NetAdapter | Format-Table Name,InterfaceDescription,Status,LinkSpeed
```

```
以太网   Intel(R) Ethernet Connection (18) I219-V   Disconnected   0 bps
WLAN     Intel(R) Wi-Fi 6 AX201 160MHz              Up             2.4 Gbps
```

两个问题同时存在：

1. **网段不匹配**：PC 只有 `192.168.0.13`（WLAN），单板是 `172.16.1.69/24` → 跨网段直连必然不通；
   `arp -a | Select-String "172.16"` 也查不到任何条目，与现象吻合。
2. **物理链路未建立**：有线网卡 `Disconnected / 0 bps`，说明 I219-V 口上根本没有 link。

### 3.4 第三步：修好之后

- 网线插好后重新插拔一次（触发自协商），网卡 link 起来；
- 给有线网卡加同网段地址：

```powershell
New-NetIPAddress -InterfaceAlias "以太网" -IPAddress 172.16.1.100 -PrefixLength 24 -SkipAsSource $true
```

（`-SkipAsSource` = 附加地址，WLAN 的 `192.168.0.13` 与上网不受影响；不要设网关。）

- 结果：

```
来自 172.16.1.69 的回复: 字节=32 时间<1ms TTL=255
数据包: 已发送 = 4，已接收 = 4，丢失 = 0 (0% 丢失)
```

`TTL=255`、0 跳，符合"直连"的特征。

**ping 通同时反向证明了一整条链**：烧写完整 → Bootloader 校验 Slot A 通过 → 跳转成功 → App 跑到 `MX_LWIP_Init()` → PHY link up → lwIP 回 ICMP。

## 五、确认的坑（重要，务必记住）

### 5.1 调试器下载 ≠ 烧写脚本（meta 不会更新）

- ST 扩展 / GDB 下载**只按 ELF 的 load 段写 App 区**，不会烧 Bootloader，也不会写 `0x0800FFD0` 的 meta。
- 在 GDB 控制下运行时（F5 → 停在 `main` → 单步），App 是**直接跑的，不经过 Bootloader 校验**，所以随便改代码随便调，没问题。
- 但**一旦退出调试 / 按板子复位**，走的是 Bootloader → 校验 meta → CRC 与实际 App 内容不符 → `NO APP`，板子起不来、ping 不通。

### 5.2 `Flash App Only` 的隐患（**待修**）

`flash_app.cmd` 只做 `objcopy` + 烧 `0x08010000`，**不重算 meta**。因此：

- 首次 `Flash Both` 之后**没有再改代码**，用它重烧是安全的（内容没变，CRC 不变）；
- 但**只要改了 App 代码并重新编译**，meta 里的 `img_len`/`img_crc32` 就是过期的 → 复位后 Bootloader 判 Slot A `INVALID` → `iap_slot_rollback()` 找不到有效槽 → **`NO APP`**。

**修正路线（待定，三条）**：

| 路线 | 做法 | 代价 |
|---|---|---|
| A | 明确把 `Flash App Only` 定位为"调试用/同版本重烧"，任务说明里写清"改代码后不能单独用它脱机运行" | 零成本，但语义与任务名不符 |
| B | 改 `flash_app.cmd`：烧 App 后**擦除 Sector 3（`0x0800C000`）并重写 meta 48 字节**，让任务名副其实 | 需要扇区级擦除能力（`ST-LINK_CLI -SE 3`，或借助 OpenOCD `flash erase_sector 3 3`）；Sector 3 不含 Bootloader 代码，擦它安全 |
| C | 让 **App 启动时自算 CRC 并更新 meta**（App 侧已有 Flash 擦写驱动，见 `net_config.c` 写 Sector 11） | 需在 App 增加逻辑；优点是不依赖烧写脚本 |

> 注意设计约束：meta 必须落在 **Sector 3（`0x0800C000–0x0800FFFF`）**，因为 Bootloader 代码只能占 sectors 0–2，
> 而 Sector 3 是运行期允许被擦除的标志扇区。`0x0800FFD0` 正是这个设计。

### 5.3 ST-Link 一连上就 halt 内核

`ST-LINK_CLI -c SWD ...`（以及 ST-LINK Utility GUI）连接即停核。此时 ping 立刻不通、TCP 断开，
**不要误判成固件坏了**。读寄存器后记得 `& $cli -c SWD -Rst` 让它跑起来。

### 5.4 其它

| 坑 | 说明 |
|---|---|
| PC 有线网卡 `Disconnected` | 重插网线触发一次自协商即可恢复；排查时**先看 `Status`，再看网段** |
| 串口 log | USART1/2/3 **都是 RS485**（`PA9/PA10` + `PA11` 作 RE/DE），必须用 USB-RS485 接 A/B；拿 USB-TTL 直接接 PA9/PA10 收不到数据 |
| `-r32` 行为 | v3.6 每次只回 1 个 word，逐个地址读 |
| 全片擦除的副作用 | `Flash Both` 的 `-ME` 会清掉 Sector 11 的 `net_config`（IP 配置表），恢复默认；同时会把 `0x0800FFF8` 的 boot_request 恢复为 `0xFFFFFFFF` |
