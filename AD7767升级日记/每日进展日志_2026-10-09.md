**卡点 / 意外发现**
1. **"20MHz 外部时钟 / MCO 不用" 被误读**：该时钟是 PHY 的 25 MHz 晶振（X3），与 AD7767 无关。三片 AD7767 各自有独立 1.024 MHz VC-TCXO（X4/X5/X6），MCU 不提供 MCLK。
2. **PHY 复位脚矛盾**：`gaojingdu_santantou_STM_GPIO.xlsx` 写 PF12(pin 60)，而 `CubeMX_config_diff_V3.md` 与现有 `gpio.c` 都是 PF11。**已按用户确认取 PF12**，需在 T0.1 一并清理 PF11 残留。
3. **三路 EXTI 物理不可行**：PA15 与 PG15 共用 EXTI15，`SYSCFG_EXTICR4` 只能二选一。已改为"PH12 独享 EXTI12 + PA15 触发时电平门控读 PG15"。
4. **"24 点平均 + 80 ms 帧周期"数学不可行**：32000 ÷ 24 = 1333.33 点/s（750 µs/点），而 80 点/帧要求 1 ms/点。若用定时器每 1 ms 取数，每秒丢弃 333 点（25%）并引入混叠。**已改为 32 点平均**（32 × 31.25 µs = 1000 µs），帧周期精确 80 ms。
5. **lwIP 堆风险前置识别**：738 B × 12.5 帧/s 在途数据约 8.8 KB，而 `MEM_SIZE = 10 KB`，余量仅 12%（498 B 帧时为 92%）。必须前置加固（T0.2）。
6. **SPI 时钟实际是"超频"而非"欠频"**：`spi.c` 三路预分频器均为 `_2` → SPI1=42 MHz、SPI2/3=21 MHz。**AD7767 的 SCLK 上限约 12 MHz（t8）**，现配置严重超标。目标 10.5 MHz 是"降下来但仍够快"的平衡点，同时必须把 MODE 0 改为 **MODE 1（CPOL=0, CPHA=1）**。
7. **旧版 `spi_read_adc()` 不能在 32 kHz ISR 中用**：它调 `HAL_SPI_TransmitReceive(..., timeout=10)`，异常时会在 ISR 内阻塞 10 ms。**必须改寄存器直驱 + DWT 超时**。
8. **既有遗留 bug 与本次改造冲突**：`代码Bug排查报告.md` 的 ADC-1（`Ads8354ReadConvers` 传 `hspi2/3` 但 `Ads8354Init()` 只初始化 SPI1 的 CFR）与 ADC-2（单 SDO 模式读 6 字节可能帧错位）在新版本必须一并消灭——AD7767 帧结构（24 bit、无填充）比 ADS8354 更严格。

**关键数据**
- AD7767 输出率：32 kSPS（31.25 µs/样本），由 1.024 MHz MCLK ÷ 32
- 32 点平均 → 1 ms/点 → 1000 点/s/通道
- 80 点/帧 → 80 ms/帧 → **12.5 帧/s**
- 帧长 **738 字节**（7 + 720 + 11），吞吐 **9.2 KB/s**
- ISR 预算：31.25 µs 内需读 2 片（PA15 中断），目标 <11 µs（35%）
- SPI 目标：SPI1 = 84/8 = **10.5 MHz**，SPI2/3 = 42/4 = **10.5 MHz**

**关键发现：纠正了一处计划中的技术错误（PA15 / JTAG）**

原计划写：PA15 用作 `DRDY_AD7767_3` 前"需先 `__HAL_AFIO_REMAP_SWJ_NOJTAG()` 释放 JTDI"。

**这是错的。** 实测与源码核对结论：
- `stm32f407xx.h` 中**没有 `AFIO_TypeDef`**，HAL 的 `stm32f4xx_hal_gpio_ex.h` 里也**只有 `GPIO_AF0_SWJ`（AF 选择符），没有 SWJ remap 宏**
- 全工程 grep `MAPR|SWJ|AFIO` 零命中（除 legacy 头文件里一个无关别名）
- **AFIO/MAPR 是 STM32F1 的机制**；STM32F4 的调试引脚复位后默认挂在 AF0(SWJ)，**把它重新配置成 GPIO 或其它 AF 就自动释放**，不需要任何 remap 调用

旁证：现有工程把 **PB3/PB4 直接当 SPI1_SCK/MISO 用**（它们是 JTDO/NJTRST），且从未调用过任何 remap —— 一直工作正常，正说明 F4 无需 remap。

⇒ 结论：PA15 直接 `HAL_GPIO_Init(..., GPIO_MODE_INPUT, GPIO_PULLUP)` 即可，**SWD(PA13/PA14) 不受影响，调试保持可用**。计划文档已修正。

**T1.1 关键设计取舍：把新引脚放在 CubeMX 管不到的地方**

`CubeMX_config_diff_V3.md` 明确警告"不要直接 hand-edit `.ioc`"。同时我无法驱动 CubeMX GUI 去点引脚。所以采取"**代码为主、`.ioc` 同步**"的策略：

- 新建 `Core/Src/bsp_pins.c` + `Core/Inc/bsp_pins.h`（**非 CubeMX 管理文件**）承载全部新引脚的 GPIO 初始化

### 二、坏消息：CubeMX 删掉了 `cmake/stm32cubemx/CMakeLists.txt` 里的手工定制

**症状（configure 阶段直接失败）**：
```
CMake Error at Bootloader/CMakeLists.txt:61 (add_library):
  No SOURCES given to target: STM32_Drivers_Boot
```

**根因**：CubeMX 只认识它自己生成的内容，不认识用户追加的段落，所以整段删除：
```cmake
set(MX_LINK_LIBS       ${MX_LINK_LIBS}       PARENT_SCOPE)   # ← 项目原有定制
set(MX_Application_Src ${MX_Application_Src} PARENT_SCOPE)   # ← 项目原有定制

```
- 第 1、2 行被删 → `app_a/b/c` 的 `add_slot_app()` 拿到空变量 → 也会失败
- 第 3 行被删 → Bootloader 的 `-Os` HAL 副本拿不到源文件 → **configure 直接报错**

> ⚠️ **这是项目原有的结构性隐患，不是本次操作引入的** —— 前两行导出在我动手之前就存在，
> 意味着**历史上任何一次 GENERATE CODE 都会同样打断构建**。只是之前没在这个工程里重新生成过，所以一直没暴露。

### 四、遗留待决策：新引脚被配置两次

现在 `MX_GPIO_Init()`（CubeMX）与 `BSP_Pins_Init()`（`bsp_pins.c`）**都配置同一批引脚**：

| 引脚 | CubeMX 生成 | `bsp_pins.c` | 谁生效 |
|---|---|---|---|
| `DRDY ×3` | 输入 + **NOPULL** | 输入 + **PULLUP** | `bsp_pins.c`（后执行） |
| `SYNC_PD ×3` | 输出 + **NOPULL** | 输出 + **PULLDOWN** | `bsp_pins.c` |
| `MII_INT` | 输入 + **NOPULL** | 输入 + **PULLUP** | `bsp_pins.c` |
| `MCU_IN1` | 输入 + **NOPULL** | 输入 + **PULLUP** | `bsp_pins.c` |
| 其余输出 | 一致 | 一致 | 无差异 |

- **功能上无冲突**（`main.c` 中 `MX_GPIO_Init()` 先跑，`BSP_Pins_Init()` 在 `USER CODE 2` 后跑，后者覆盖前者）
- **维护上是隐患**：两处配置同一引脚，将来改 `.ioc` 的上下拉会被 `bsp_pins.c` 静默覆盖
- **建议（待用户定）**：既然 CubeMX 已证明能完整生成这些引脚（路线 A），**删掉 `bsp_pins.c` 的 GPIO 初始化**，改由 `.ioc` 设置上下拉；`bsp_pins.c` 只保留 AD7767 相关的非 GPIO 辅助（若有）。或者反过来保留 `bsp_pins.c` 并在 `.ioc` 中把这几个引脚设为 NOPULL 并接受"代码层覆盖"。**倾向前者（单一权威源）**

**结论：仍在安全范围（68.05%，余 14.5 KB），48 KB 门禁未受威胁。** 但这是一条需要留意的新事实：**Bootloader 尺寸会随 HAL 模块使能情况变化，不只是随 Bootloader 自身代码变化。**
